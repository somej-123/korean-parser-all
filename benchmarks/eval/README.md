# 정답 세트와 요소별 평가

파서가 "얼마나 정확한가"를 숫자로 잰다. 고칠 때마다 다시 돌려 좋아졌는지, 다른 곳이 나빠지지 않았는지 확인한다.

```bash
pip install -e "../..[pdf,eval]"
python synth.py --out data --docs 12 --scans 4      # 정답이 있는 문서 만들기 (LibreOffice 필요. Windows는 기본 설치 폴더도 찾는다)
python evaluate.py data --out report.md              # korean-parser 평가
python evaluate.py data --baseline                   # Docling 기본 출력도 같은 지표로 (비교 기준)
python evaluate.py --hwpx ../corpus/samples_web      # HWPX: 한컴오피스 미리보기 글과 비교
python evaluate.py data --formats pdf                # 한 형식만
```

## 정답 세트

**합성 문서** (`synth.py`): 정답(구조화된 명세)을 먼저 만들고 그 명세로 DOCX를 쓴다. LibreOffice로 PDF를,
쪽 그림으로 스캔 PDF(텍스트 레이어 없음, OCR 경로)를 만든다. 같은 정답으로 세 형식을 모두 잰다.
정답이 파서와 상관없이 명세에서 나오므로 파서를 고쳐도 기준이 흔들리지 않는다.

한국 제안요청서를 흉내 낸다.

- 로마 숫자·"1." 장절 제목: 제목 스타일을 쓴 문서와 굵고 큰 글씨 문단으로 쓴 문서를 번갈아
- □ ○ - ※ 개조식, 숫자·영문 약어가 섞인 문장("5.0점", "(20)", "HWPX와", "30분 이내")
- 줄·쪽을 넘어가는 긴 문단
- 첫 열 세로 병합, 가로 병합이 있는 표. 80%는 칸마다 선이 있는 표, 20%는 위아래 선만 있는 표

**HWPX 미리보기**: 한컴오피스는 HWPX를 저장할 때 앞부분 글(`Preview/PrvText.txt`)을 함께 넣는다. 한컴오피스가
직접 만든 글이므로 우리 파서와 독립된 정답이 된다. 미리보기 글자가 우리 결과에 같은 순서로 나오는 비율을 잰다.

## 지표

| 지표 | 뜻 |
|---|---|
| 글자 오류율 (CER) | 공백을 뺀 전체 글의 편집 거리 ÷ 정답 글자 수. 글자를 빠뜨리거나 잘못 읽거나 순서가 바뀐 정도. 낮을수록 좋다 |
| 어절 F1 | 띄어쓰기 단위(어절)가 정답과 같은 비율. 띄어쓰기 복원 품질 |
| 블록 재현율 | 정답 문단·제목 중 결과에서 찾은 비율 |
| 읽기 순서 | 짝지은 블록 중 순서가 맞는 쌍의 비율 (켄달 타우를 0~1로) |
| 제목 재현율·정밀도·단계 | 제목을 제목으로 찾았는지, 제목이 아닌 것을 제목으로 보지 않았는지, 같은 단계끼리 묶였는지 |
| 표 TEDS / TEDS-S | 표를 HTML 트리(table→tr→td, 병합 포함)로 보고 트리 편집 거리로 잰 유사도 (PubTabNet 지표). TEDS-S는 칸 글을 무시한 구조만 |

## 이 평가로 찾아 고친 것

| 문제 | 지표 변화 |
|---|---|
| OCR 글 방향 분류기가 한국어 가로줄을 뒤집힌 줄로 보고 엉뚱한 글자로 읽음 → 분류기 끔 | 스캔 글자 오류율 52.8% → 13.2%, 블록 재현율 0.45 → 0.92 |
| 쪽을 넘어간 표가 둘로 나뉨 → 열 너비가 같은 다음 쪽 첫 표를 이음 | PDF 표 TEDS 0.83 → 0.97 |
| Docling 읽기 순서가 쪽 위의 표·주석을 아래 문단 뒤에 둠 → 한 단 쪽은 위치 순서로 | PDF 글자 오류율 3.0% → 1.2% |
| "시 30분" → "시30분": 한글 뒤 숫자·영문은 새 어절로 (제3조 제외) | 어절 F1 상승 |
| 짧은 제목에서 텍스트 레이어 글을 버리고 Docling 글("· Ⅰ 사업개요")을 씀 → 다른 글자 수로 판단 | |
| 위아래 선만 있는 표를 표 구조 인식 모델에 맡김 → 줄이 넘어간 칸이 다른 행으로 나뉘고, 쪽을 넘어간 나머지는 표로 찾지 못함 → 글 위치로 열·행을 정하는 격자, 앞 쪽 열 경계로 다음 쪽 나머지를 읽음 | 열린 표 TEDS 0.897 → 1.000 |
| Docling이 쪽 맨 아래 표를 다음 쪽 앞부분 뒤에 둠 → 쪽 순서도 바로잡음 | PDF 글자 오류율 0.9% → 0.0%, 표 TEDS 0.972 → 0.993 (위 줄과 함께) |
| OCR 글은 공백이 대부분 빠지는데('계약방법:협상에의한계약') 일부가 남아 '띄어쓰기 소실'로 판단하지 못함 → 쪽 그림의 글자 사이 빈칸으로 공백을 정하고, OCR이 빠뜨리거나 'O'로 읽은 ○ □ 기호를 모양으로 되살림 | 스캔 어절 F1 0.586 → 0.887, 글자 오류율 15.5% → 13.9% |

## 알려진 한계 (결과에 그대로 드러난다)

- 위아래 선만 있는 표는 글 위치로 읽으므로, 선이 없어 보이지 않는 구조는 정할 수 없다. 첫 열이 빈 행은 위 칸과 병합된
  것으로, 다른 열의 빈 칸은 빈 칸으로 둔다 (선이 없으면 두 경우가 똑같이 보인다). 머리 행이 두 줄 이상으로 나뉜 표,
  열 사이가 글자 크기의 0.85배보다 좁은 표는 아직 시험하지 못했다.
- 굵고 큰 글씨 문단으로 쓴 DOCX 제목은 제목으로 바꾸지 않는다 (원본 구조 그대로). 청크 도구는 제목 경로에 쓴다.
- 스캔 문서는 OCR 엔진(RapidOCR 한국어 모델)의 글자 오류가 남는다 (글자 오류율 14%: '인식률'→'인식를', 'Ⅰ'→'I').
  띄어쓰기는 쪽 그림의 빈칸으로 되살리지만, 줄이 바뀐 자리와 그림과 글자 수가 맞지 않는 줄은 형태소 분석에 맡긴다.
  명사와 명사 사이('요구사항'/'요구 사항')는 그림에 빈칸이 없으면 붙이고, 형태소 분석에 맡긴 줄에서는 띄운다.
- 표 TEDS의 짝짓기를 바꿨다 (v0.7.2 이후): 예전에는 정답 표마다 낱말 집합 유사도가 가장 높은 예측 표를 골랐는데, 이 값은
  한쪽 낱말이 다른 쪽의 부분집합이면 100점이라 쪽을 넘어 여러 조각으로 나뉜 예측 표의 작은 조각과 짝지어졌다. 띄어쓰기만
  바뀌어도 점수가 오르내렸다 (스캔 synth_00, 0.73 ↔ 0.69). 지금은 글이 어느 정도 겹치는 쌍 가운데 TEDS가 높은 쌍부터
  일대일로 짝짓는다. 위 표는 바뀐 방식으로 잰 값이다 (예전 방식: 스캔 0.758, Docling 기본 PDF 0.909·스캔 0.702,
  korean-parser PDF는 같음).
- HWPX에서 문단 중간에 놓인 글상자의 글은 그 문단 앞에 나온다.
- 합성 문서는 LibreOffice 한 가지로 만든 PDF다. 한글(HWP)이 만든 PDF의 특성은 실제 문서(`../corpus/`)로 확인한다.

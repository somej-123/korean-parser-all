# 아키텍처

## 목표

1. **모든 형식을 하나의 입구로**: HWP, HWPX, DOCX, PPTX, XLSX, PDF, 스캔 이미지 → 하나의 결과 형식
2. **한국어 특화**: 한글 문서 형식, 개조식·번호 체계, 띄어쓰기, 한국어 OCR
3. **후처리 없는 HTML**: Markdown을 거치지 않고, 파싱 결과가 바로 원본처럼 보이는 화면
4. **빠짐없는 파싱**: 텍스트, 표(병합·서식), 도식(도형·연결선), 차트, 이미지, 각주, 머리말

범위: 이 프로젝트는 파서(엔진)까지만 맡는다. 분류·임베딩·검색·정보 추출은 후속 프로젝트가 맡는다 ([SCOPE.md](SCOPE.md)).

## 구조

```
입력 (DOCX ✅, HWPX ✅, HWP ✅, PDF ✅, PPTX, XLSX, 이미지)
  │
  ▼
parsers.parse(path)                 ← 단일 입구. 형식 판별 후 형식별 파서 호출
  │                                    손상·암호화 파일은 DocumentError(사용자용 메시지)
  ├─ parsers/docx/   XML 규칙 파싱 (AI 없음)
  ├─ parsers/hwpx/   XML 규칙 파싱 (AI 없음)
  └─ parsers/pdf/    Docling(레이아웃·표·OCR) → IR, PDF 텍스트 레이어·그래픽으로 보정
  │
  ▼
ir.Document                         ← 통합 문서 모델. 모든 파서의 공통 계약
  │
  ▼
enrich.enrich_korean(doc)           ← 한국어 처리 레이어 (정규화, 개조식 계층)
  │                                    PDF/OCR이면 spacing(띄어쓰기 복원)도 적용
  ▼
render/
  ├─ html.py   화면용 HTML (서식, 병합, 테두리, 이미지, SVG 도식·차트, 떠 있는 개체)
  ├─ llm.py    LLM 입력용 텍스트 (Markdown + 병합 표는 HTML + 도식은 연결 관계)
  └─ JSON      Document.model_dump_json() 그대로
  │
  ▼
chunk.chunk(doc)                    ← 검색용 조각 (제목 경로, 표 보존, 블록 id·쪽·좌표). LLM 렌더러로 글을 만든다
```

**밖에서는 하나의 입구, 안에서는 형식별 분리.** 사용하는 쪽은 형식을 몰라도 되고, 형식별 파서는
서로를 모른 채 "IR로 돌려준다"는 약속만 지킨다. PDF 엔진을 바꿔도 HTML·LLM 출력 코드는 그대로다.

## 통합 문서 모델 (IR)

`korean_parser/ir.py`. pydantic 모델이라 JSON으로 저장·복원할 수 있다.

| 요소 | 담는 정보 |
|---|---|
| `Paragraph`, `Heading` | 서식 있는 글 조각(`Text`), 문단 서식(정렬·들여쓰기·간격·테두리), 자동 번호(`ListInfo`, 화면 표시 그대로 계산한 "가." 등), 개조식 계층(`OutlineInfo`) |
| `Table` | 행·셀, `row_span`/`col_span`, 셀 배경·테두리·세로 정렬, 열 너비, 셀 안의 블록(중첩 표 포함) |
| `Drawing` | 도형(`Shape`: 모양, 좌표, 회전, 채우기, 선, 화살표, 연결 대상, 글상자), 떠 있는 배치(`Anchor`) |
| `Chart` | 종류, 방향, 묶음/누적, 범주, 계열 값과 색 |
| `Figure`, `ImageRef` | 이미지(원본 바이트를 base64로 보관), 크기, 대체 텍스트 |
| `Equation` | 수식 원문 (한글 수식 스크립트 / LaTeX) |
| `Anchor` | 떠 있는 표·도식의 배치 (글 옆으로 흐름 / 위아래 / 글 앞·뒤로 겹침, 기준과 위치) |
| `Note` | 각주·미주 |
| `Provenance` | 어떤 파서가 원본의 어디(페이지, 좌표)에서 만들었는지, 신뢰도 |
| `Meta` | 제목·작성자·날짜, 원본 파일 해시(SHA-256)·크기, 파서 버전, 쪽 수와 그 출처 |

`Document.schema_version`(`IR_VERSION`)으로 형식 버전을 밝힌다. 길이는 모두 pt, 색은 `#RRGGBB`. 모든 블록에 `id`가 있어 LLM 답변의 근거를 화면 위치로 되짚을 수 있다
(HTML의 `data-kp-id`, LLM 텍스트의 `<!-- b12 -->`).

`Provenance`는 나중에 같은 문서를 여러 파서로 처리하고 요소별로 더 나은 결과를 고를 때(예: PDF 텍스트는
텍스트 레이어, 표는 표 인식 모델) 근거로 쓴다.

## HTML 렌더링 원칙

- 문서 모델에서 바로 만든다. Markdown을 거치지 않으므로 병합 셀, 테두리, 색, 도형이 사라지지 않는다.
- 한 파일로 완결: CSS와 이미지(data URI)를 모두 안에 넣는다. 외부 요청 없음.
- 원문 텍스트는 모두 이스케이프하고, 링크는 `http(s)`, `mailto`, `#`만 허용한다. 색과 글꼴 이름은
  정규식으로 검증한 값만 CSS에 넣는다.
- 한국어 줄바꿈은 어절 단위(`word-break: keep-all`).
- Word의 문단 간격은 앞뒤를 더하므로 CSS margin 대신 padding을 쓴다.
- 도형은 SVG, 도형 안 글은 `foreignObject`의 HTML(한국어 자동 줄바꿈 때문).
- 떠 있는 개체: 글이 옆으로 흐르면 `float`, 글과 겹치면 페이지 기준 `position:absolute`.

## HWP 5.0 파싱에서 알아 둘 점 (`parsers/hwp/`)

- HWP 5.0과 HWPX는 같은 문서 모델이다. 바이너리 레코드를 HWPX의 header.xml·section.xml 모양 XML(HWPX 파서가 읽는
  요소·속성만)로 옮기고, 그 뒤는 HWPX 파서(`HwpParser`는 `HwpxParser`를 이어받음)가 그대로 변환한다.
- 파일은 OLE 복합 파일이다 (olefile). FileHeader 속성: 압축(스트림을 raw deflate로 풂), 암호, 배포용(본문 암호화 → 열 수 없음 안내).
- 레코드 머리 4바이트 = 태그 10비트 | 단계 10비트 | 크기 12비트(0xFFF면 뒤 4바이트). 본문은 단계로 나무를 만든다
  (문단 → 글자·컨트롤 → 표 → 칸 → 칸 문단). DocInfo는 모양 레코드가 ID_MAPPINGS 아래에 매달려 있어 평평하게 읽는다.
- 문단 여백·간격은 실제의 **2배**로 저장된다 (HWPX의 hp:default와 같다). 줄 간격 '고정·최소'도 2배.
- 표 칸(LIST_HEADER): 문단 수 2바이트 + 2바이트 + 속성 4바이트(세로 정렬은 5~6비트) 뒤에 열·행·병합·크기·여백·테두리.
  칸의 문단은 LIST_HEADER의 자식이 아니라 그 뒤에 오는 형제 레코드다.
- 테두리선 종류 0은 '없음', 1이 실선. 테두리/배경·번호·글머리표 id는 1부터, 글자·문단 모양과 스타일 id는 0부터.
- 문단 글(PARA_TEXT)의 제어 문자: 1글자(줄 바꿈 10, 문단 끝 13, 묶음 빈칸 30 …)와 8글자(탭 9, 필드 끝 4, 컨트롤 11 등).
  확장 컨트롤(표·그림·수식·머리말·각주·필드 시작)은 문단의 CTRL_HEADER 레코드와 나온 차례로 짝이 된다.
- 그리기 개체(gso): CTRL_HEADER 아래 SHAPE_COMPONENT 하나. 컨트롤 id(`$rec` `$ell` `$arc` `$lin` `$pol` `$cur` `$col`
  `$con` `$pic`)가 맨 위 개체는 두 번, 묶음 안 개체는 한 번 나온다. 그 뒤 묶음 안 위치, 원래·현재 크기, 회전,
  renderingInfo(확대·회전 쌍 수 2바이트, 이동 행렬, 쌍마다 확대·회전 행렬. 행렬은 double 6개 = HWPX의 e1~e6),
  선(색, 굵기 HWPUNIT, 속성: 종류 0~5비트·화살표 10~21비트), 채우기, 그림자 16바이트, 개체 id(HWPX instid).
  묶음은 선·채우기 대신 안 개체 수와 id가 오고, 안 개체의 SHAPE_COMPONENT가 그 자식이다.
  모양 레코드(사각형 곡률+꼭짓점 4개, 타원 중심·축, 다각형·곡선 점 개수 4바이트+점, 연결선 끝의 개체 id·연결점)와
  글상자(LIST_HEADER + 형제 문단)도 SHAPE_COMPONENT의 자식이다. 이를 hp:rect 등으로 옮겨 HWPX의 `ShapeReader`가 그린다.
- 채우기에서 종류가 0이면 뒤에 4바이트가 더 있다. 그러데이션 값 크기는 공개 문서(2바이트)와 달리 종류 1바이트,
  나머지 4바이트다 (hwplib 확인). 연결선 레코드는 공개 문서에 없어 hwplib으로 확인했다 (실제 파일 표본 없음).
- 사각형 곡률(%)은 짧은 변에 대한 모서리 반지름의 비율이다 (50이 반원). 제안요청서의 글상자는 10%.
  기본 둥근 사각형(짧은 변의 1/6)과 달라 `ShapeReader`가 경로로 그린다 (HWPX의 `ratio`도 같다).
- 문서 요약 정보(HwpSummaryInformation)는 직접 읽는다. olefile은 UTF-16 문자열 길이를 바이트로 읽어 뒤 속성까지 섞었다.
- 실제 제안요청서 5개: 한컴오피스 미리보기 글 재현율 1.000, 본문 글자 수가 레코드 글자 수와 같다 (정규화로 바뀐 'ｏ'·'ㆍ' 등만 다름).

## HWPX 파싱에서 알아 둘 점

- HWP는 스타일 상속이 없다. 문단·글자가 가리키는 문단 모양(`paraPr`)과 글자 모양(`charPr`)에 값이 모두 들어 있다.
- 문단 여백은 `hp:switch` 안에 두 벌로 저장된다. `hp:default`(구버전 호환)는 실제의 **2배** 값이므로 `hp:case`를 쓴다.
- 그리기 개체는 원래 크기(`orgSz`) 좌표에 `renderingInfo` 행렬(이동 · 확대·회전 쌍 …)을 곱해 위치를 얻는다.
  묶음 개체 안의 행렬은 이미 묶음 좌표계 기준이다.
- 연결선의 `subjectIdx`(0 위, 1 오른쪽, 2 아래, 3 왼쪽)로 꺾인 연결선의 경로를 정한다.
- 표 칸·글상자 안에서는 마지막 줄 뒤 줄 간격을 넣지 않는다 (HTML에서 `margin-block`으로 보정).
- 개요 번호는 구역(`secPr`)의 `outlineShapeIDRef` 번호 정의를 쓰고, 건너뛴 상위 단계는 시작값으로 채운다.
- 쪽 배경(`pageBorderFill`)에 그림 채우기를 쓰는 서식이 많다 (보고서 표지의 색 띠 등).

## PDF 처리에서 알아 둘 점

- 글은 Docling이 아니라 PDF 텍스트 레이어(pdfium)에서 다시 읽는다. Docling 글은 공백이 자주 빠져
  형태소 분석으로 복원해도 틀리는 곳이 남는다("2026 년문서파싱"). 텍스트 레이어의 실제 공백 글자는 그대로 쓰고,
  pdfium이 끼워 넣은 공백은 글자 사이 실제 간격이 있을 때만 쓴다. 한글과 영문·숫자 사이의 좁은 간격(조판 프로그램의
  자동 간격일 수 있음)과 한글-한글로 끊긴 줄바꿈 자리만 형태소 분석으로 정한다. 다시 읽은 글이 Docling 글과
  내용이 다르면 Docling 글에 형태소 분석 띄어쓰기를 쓴다. 예시 PDF의 어절 F1: 0.778 → 0.929.
- 표 구조는 괘선으로 읽는다 (`parsers/pdf/rules.py`). 한국 공공 문서의 표는 거의 모두 칸마다 선이 있고, 표 인식 모델
  (TableFormer)은 병합 칸이 많은 평가표·서식에서 칸을 섞는다. 선 읽기: 선·얇은 사각형·윤곽선 사각형의 변, 점선 조각
  (1.2×0.7pt 같은 작은 조각)은 이어 붙인다. 격자: 수평선 위치 = 행 경계, 수직선 위치 = 열 경계, 좌우 바깥선이 없는 표는
  수평선의 가로 범위가 표 범위다. 칸 경계에 선이 없으면 이웃 칸과 합쳐 병합 칸이 된다(사각형이 아니면 괘선 표가 아닌 것으로
  보고 포기). Docling 표 영역이 표의 일부만 덮으면 이어진 선을 따라 넓히고, Docling이 한 표를 둘로 나눴으면 하나로 합친다.
  격자가 2행 이하(머리 행에만 선)이거나 표 영역 글자의 10% 넘게 격자 밖에 있으면 Docling 결과를 쓴다.
- 위아래 선만 있는 표('열린 표', `parsers/pdf/open_table.py`): 세로선 없이 위·머리 행 아래·아래에만 가로선이 있으면 선으로
  열을 알 수 없다. 표 구조 인식 모델은 줄이 넘어간 칸을 다른 행으로 나눴다. 텍스트 레이어 글자 위치로 격자를 만든다.
  열 = 머리 행 글 덩어리(글자 크기 0.85배보다 넓은 빈칸에서 나눔) 수, 경계 = 이웃한 머리 글 사이에서 본문 글이 가장 적게
  걸친 자리. 행 = 앞 줄의 같은 열 글 뒤에 이 줄 첫 낱말이 들어갈 자리가 없었으면 넘어간 줄, 아니면 새 행 (첫 낱말 끝은
  잉크 간격이 아니라 실제 공백 글자로 본다. '1,250,000,000원'은 잉크 사이가 넓다). 열 경계를 가로지른 글은 가로 병합 칸,
  빈 첫 열은 위 칸의 세로 병합으로 본다. 앞 쪽 마지막 블록이 이런 표이고 다음 쪽 첫 블록 자리에 같은 가로 범위의
  가로선 두 개가 있으면 앞 표의 열 경계로 그 사이를 읽는다 (머리 행도 세로선도 없어 Docling이 표로 찾지 못한다).
  정답 세트 열린 표 8개 TEDS 0.897 → 1.000. 표의 신뢰도는 0.8 (괘선 표 1.0).
- 처리 시간: 텍스트 레이어가 있으면 Docling을 표 구조 인식 모델 없이 먼저 돌리고(레이아웃만), 괘선으로 읽지 못한 표가
  있는 쪽만 모델을 켜고 다시 돌린다. 모델이 처리 시간의 절반 가까이를 차지했다 (46쪽 문서 126초 → 85초, CPU 4스레드).
  모델을 끄면 표 안의 글이 따로 나오므로, 표가 이미 담은 글(괘선 격자·모델 표 영역 안)은 건너뛰고 그 밖의 글(표에 묶인 주석)은 본문에 둔다.
  괘선 격자가 2행 이하이면 마지막 행에서 두 칸 이상이 같은 높이에 여러 줄을 두었는지(선 없는 행) 보고 모델에 맡길지 정한다.
- 끊긴 문단 잇기: Docling은 내어쓰기한 개조식 문단의 다음 줄이나 쪽을 넘어가는 문단을 다른 문단으로 뗀다. 앞 문단의 마지막 줄이
  본문 오른쪽 끝까지 찼고(본문 폭의 절반 이상), 문장으로 끝나지 않았고, 뒤 문단이 개조식 기호로 시작하지 않으며 글자 크기·굵기가
  같고, 바로 아랫줄(또는 다음 쪽 첫 문단)이면 잇는다. 이은 자리의 공백은 줄 합치기와 같은 규칙(한글-한글이면 형태소 분석)으로 정한다.
- 쪽을 넘어간 표: 앞 쪽의 마지막 블록이 표이고 다음 쪽 첫 블록이 열 수·열 너비가 같은 표면 잇는다(되풀이한 머리 행은 뺀다).
  Docling이 표로 찾지 못한 괘선 표(쪽을 넘어간 짧은 나머지, 서식 칸)는 선 묶음만으로 찾는다 (그림 영역 안의 눈금선은 제외).
- 읽기 순서: 쪽 안에 나란히 놓인 블록이 없으면(한 단) 블록을 세로 위치 순서로 둔다. Docling 순서가 쪽 위의 표를 아래 문단
  뒤에 두는 경우가 있다. 다단 쪽은 Docling 순서를 쓴다. 쪽 순서도 바로잡는다: Docling이 쪽 맨 아래 표를 다음 쪽 앞부분 뒤에
  둔 경우가 있었다 (정답 세트 synth_11, PDF 글자 오류율 8.9%의 원인).
- 한글-영문·숫자 사이의 좁은 간격: 한글 뒤 숫자·영문은 새 어절('시 30분', 단 '제3조'), 숫자·영문 뒤 한글은 형태소 분석
  ('30분', 'OCR이' / 'PDF 기준').
- OCR: RapidOCR의 글 방향 분류기를 끈다. 한국어 가로줄을 뒤집힌 줄로 잘못 보고 엉뚱한 글자로 읽었다 (정답 세트 스캔 글자
  오류율 52.8% → 13.2%).
- OCR 띄어쓰기 (`parsers/pdf/ocr_spacing.py`): OCR은 줄 안의 공백을 대부분 빠뜨리지만 일부는 남겨 '띄어쓰기 소실' 판단에
  걸리지 않았다. 텍스트 레이어의 글자 간격처럼, 쪽 그림(216dpi)에서 OCR 줄마다 잉크 없는 세로 띠의 폭을 글자 높이(em)
  배수로 재서 공백을 정한다. 공백 기준은 글꼴마다 달라(바탕 0.42em, 고딕 0.33em 안팎) 문서 전체 빈칸 폭 분포를 오츠
  방법으로 두 무리로 갈라 정한다. 공백으로 나뉜 조각 폭과 글자 예상 폭(한글 1, 숫자 0.52 …)을 동적 계획법으로 맞춰 공백
  자리를 고르고, 한글과 숫자·영문·문장부호가 맞닿은 자리는 기준의 0.6배로 본다(영문 글꼴의 공백이 좁다). 숫자 바로 뒤
  한글('2026년')과 닫는 문장부호 앞은 띄우지 않는다. 줄 맨 앞의 1em 조각이 □ ○ ■ ● - 모양이면 OCR이 빠뜨리거나 'O'·'ㅇ'으로
  읽은 개조식 기호로 되살린다. 그림과 글자 수가 맞지 않는 줄과 줄이 바뀐 자리는 형태소 분석(`SpacingFixer.respace_ocr`)에
  맡긴다. 정답 세트 스캔 어절 F1 0.586 → 0.887, 글자 오류율 15.5% → 13.9%.
- 칸·문단 안의 글은 기준선으로 줄을 묶고 줄 안에서는 왼쪽부터 읽는다. 괄호·숫자를 따로 그리는 PDF에서 그리는 순서를
  따르면 글자 순서가 뒤섞인다.
- 나중에 그려진 그림이 글을 덮는지 볼 때 그림의 투명도(알파)를 확인한다. Word는 투명한 그림을 글 위에 두기도 한다.
- Docling은 무엇이 제목·표·그림인지와 읽기 순서를 잘 찾지만 글자 서식을 주지 않는다. PDF 텍스트 레이어의 글자마다
  크기·굵기·색이 있으므로 Docling 영역 안의 글자를 읽어 되살린다.
- 글자 크기 = 글꼴 크기 × 글자 행렬의 배율. 글꼴 크기만 보면 행렬로 축소해 그린 PDF에서 수십 배 큰 값이 나온다.
- 굵은 글꼴이 없을 때 '채우기+윤곽선'으로 그린 글(가짜 굵게)도 굵게로 본다.
- Docling이 차트·캡션·제목·도식을 그림 하나로 묶는 경우가 있다. 그림 영역 안의 실제 이미지·벡터 개체를
  10pt 간격으로 묶어 그림을 나누고, 묶음 밖의 글은 원래 블록(제목·문단)으로 되돌린다.
- 머리말로 분류된 글이라도 한 쪽에만 나오면 본문으로 본다 (쪽 맨 위의 '(단위: 억원)' 등).
- 고정 배치(fixed): 원본 PDF의 사본에서 글자 개체를 지우고 그린 그림을 바탕으로 깔고, 그 위에 SVG `<text>`를
  원래 기준선 위치에 `textLength`로 원래 너비에 맞춰 올린다. 그릴 때 나중에 그려진 불투명 도형에 덮이는 글
  (템플릿의 숨은 글, 그림자용 겹친 글)과 보이지 않게 그린 글은 제외한다.
- 글자 묶음(run)의 간격은 잉크 상자가 아닌 글자 기준점(origin)과 글자 폭(advance)으로 잰다. 폭 정보가 깨진
  글꼴(모든 글자 폭이 글자 크기만큼)은 같은 줄 이웃 글자의 보통 간격을 폭으로 본다. pdfium이 끼워 넣은 공백은 단어 경계다.
- '덮개' 판정과 그래픽 범위는 잘라내기 경로(clip path)로 좁힌 보이는 범위를 쓴다.
- 사용자 정의 영역(PUA) 문자만 든 글자 개체(기호 글꼴의 글머리 □ 등)는 브라우저가 그릴 수 없으므로 바탕 그림에 남긴다.

## 그림 형식 바꾸기 (`images.py`)

- 한글·워드 문서의 로고·도식은 WMF·EMF(윈도 메타파일)인 경우가 많은데 브라우저가 그리지 못한다. `parse()`가 파싱 뒤에
  PNG로 바꿔 넣고(`convert_images=True`), 원래 mime을 `Image.converted_from`에 남긴다. 바꾼 그림의 '표시할 수 없음' 경고는 지운다.
- Pillow는 TIFF를 어디서나, 메타파일을 Windows에서만(GDI) 그린다 (150dpi). 그 밖에는 LibreOffice로 문서의 그림을 한 번에
  바꾼다 (실행에 5초 안팎). LibreOffice는 메타파일을 A4 쪽 가운데에 그리므로 흰 여백을 잘라 낸다.
- 실제 문서: 누리집 제안요청서(HWP)의 WMF 로고가 경고 대신 그림으로 나온다.

## 청크 도구에서 알아 둘 점

- 제목 경로는 `Heading` 블록과 '제목처럼 쓰인 번호 문단'으로 만든다. 판단은 `heading_guess.py`(`TitleFinder`) 하나로,
  한국어 처리 레이어가 같은 판단으로 `Paragraph.heading_guess`(추정 단계, 근거)를 붙인다. 기준: 번호·기호로 시작, 표지를 뺀
  글 2~40자, 문장으로 끝나지 않음, ':' 없음('사업기간 : 7개월'), 목차 줄 아님, 번호면 본문보다 굵거나 크고(1.05배·0.9pt 초과),
  기호(□ ○ ◦ ㅇ - · •)면 본문보다 큼(1.1배 — 강조하려고 굵게 쓴 개조식 항목이 흔하다), ※는 제외. 추정 단계 = 바로 앞
  Heading 단계 + 그 아래에서 추정 제목 표지 종류가 처음 나온 순서. 실제 HWP 제안요청서에서 굵은 '◦ …', '- 청렴옴부즈만 …',
  15pt로 쓴 'ㅇ 사업기간 : …'이 제목이 되던 것을 이 기준으로 걸렀다. 정답 세트 DOCX 제목 재현율 0.500 → 0.961 (추정 포함).
- 제목 상자(한 칸 표) 안의 번호 문단은 본문에서 같은 종류의 번호가 쓰인 단계를 그대로 쓴다.
- 장이 바뀌면 끊고, `min_tokens`(기본 상한의 1/4)보다 작은 조각은 같은 장 안의 다음 절과 합친다.
- 큰 표는 병합 칸의 실제 위치(행·열)를 계산해 행 범위로 자르고, 경계에 걸친 세로 병합 칸은 다음 조각에 복사한다.
